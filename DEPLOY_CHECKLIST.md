## C. Fallback: create the first admin without email (`npm run admin:create`)

Use this if Brevo isn't working yet, or an admin registered but never got the
verification email. Run it in **PowerShell or cmd** (Git Bash may show the
password while you type).

```powershell
cd "C:\Users\User\Downloads\Project E-Noise\server"
$env:DATABASE_URL = "<Neon string>"
npm run admin:create
Remove-Item Env:DATABASE_URL
```

- It **only** uses the `DATABASE_URL` you set in that window (never `server\.env`),
  shows which host and database it will write to, and asks you to confirm.
- It asks for name, email and password (twice). The password isn't shown and is
  never printed; only its bcrypt hash is stored.
- New email: creates a **verified** admin who can sign in at `/login` at once.
- Existing admin with that email (e.g. registered, never verified): it asks,
  then marks it verified, sets the new password and signs out its old sessions.
  A DISABLED admin stays disabled.

## D. enoise-dev: was the old migration 017 applied?

Don't run this against `enoise-prod`. In Neon → SQL Editor on **enoise-dev**:

```sql
select filename, applied_at from schema_migrations
where filename = '017_sensor_node_id_alignment.sql';               -- 1: old 017 ran?
select conname from pg_constraint
where conname = 'tables_sensor_node_id_format';                    -- 2: new 017 already there?
select id, table_number, sensor_node_id from tables
where sensor_node_id !~ '^[A-Za-z0-9_-]{1,100}$';                  -- 3: IDs the new rule rejects
```

- **Query 1 returns no row:** nothing to do. The next `npm run db:migrate` on dev
  applies the new 017.
- **Query 1 returns a row and query 2 returns nothing:** the old 017 ran. It only
  added data (tables 1-7, sensor_status rows), no schema, so the only missing
  piece is the new constraint.
  1. Query 3 must return no rows. If it returns some, rename those node IDs in
     Table Configuration first.
  2. Run the new 017's two statements in the SQL Editor (the `schema_migrations`
     row is already there, so `db:migrate` won't run it again):
     ```sql
     ALTER TABLE tables DROP CONSTRAINT IF EXISTS tables_sensor_node_id_format;
     ALTER TABLE tables ADD CONSTRAINT tables_sensor_node_id_format
       CHECK (sensor_node_id ~ '^[A-Za-z0-9_-]{1,100}$');
     ```
  3. Query 2 now returns the constraint. The tables the old 017 inserted stay as
     dev data; delete them in Table Configuration if you don't want them.
- **Query 2 already returns the constraint:** dev is in line.
